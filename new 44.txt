# Project Development Prompt: Secure, Policy-Driven NFSU Student Placement Management System

## 1. Project Overview

Act as a senior full-stack developer, Django security engineer, database architect, and UI/UX designer.

Build a complete, secure, policy-driven **NFSU Student Placement Management System** for a coding event at the National Forensic Sciences University (NFSU).

The system must digitize the placement process, enforce placement eligibility rules, protect student information, and provide separate dashboards and permissions for different users.

**Development constraints:**
- Time limit: 1 day.
- Team size: Individual developer.
- Backend: Python with Django.
- Database: MySQL.
- Frontend: HTML5, CSS3, Bootstrap 5, and JavaScript.
- Authentication: Django authentication system.
- Authorization: Backend-enforced Role-Based Access Control (RBAC).
- Development environment: Windows 11, VS Code, Python virtual environment, and MySQL/XAMPP if compatible.
- Target: A working, demonstrable application with realistic sample data.

Prioritize a functional, secure MVP over unnecessary complexity. Do not use React or microservices.

## 2. Mandatory User Roles

Implement exactly these five application roles:

### Role 1: Admin
Responsibilities:
- Create, update, deactivate, and manage user accounts.
- Assign roles and manage user permissions.
- Manage courses, departments, and academic programmes.
- Configure placement policies and eligibility criteria.
- Approve and monitor company registrations.
- Access system-wide placement statistics and reports.
- View security audit logs.
- Manage system settings.

Restrictions:
- Only authorized administrators can create or assign privileged roles.
- Prevent unauthorized privilege escalation.
- Protect critical operations with appropriate validation and audit logging.

### Role 2: Placement Officer
Responsibilities:
- Manage registered companies and recruiters.
- Create, edit, publish, and close placement drives.
- Configure or apply placement eligibility criteria.
- Review student applications.
- Monitor applications, shortlists, offers, and final results.
- Generate placement reports.
- Review authorized audit information where explicitly permitted.

Restrictions:
- Cannot create administrators or assign privileged system roles.
- Cannot modify system-wide security settings.
- Must follow configured placement policies.

### Role 3: Course Coordinator
Responsibilities:
- View students belonging to assigned courses.
- Verify student academic details.
- Review placement eligibility.
- Monitor placement applications and outcomes.
- Generate reports for assigned courses.

Restrictions:
- Access only explicitly assigned courses and their associated students.
- Cannot modify users' roles, global policies, or other coordinators' assignments.
- Cannot access unrelated courses or unrestricted student records.

### Role 4: Recruiter / Company Representative
Responsibilities:
- Manage their own company profile.
- Submit job descriptions and placement-drive requests.
- Specify job roles, required skills, salary or CTC, location, and eligibility requirements.
- View eligible applicants for authorized company drives.
- Shortlist and reject applicants.
- Update interview stages and recruitment outcomes.
- Submit offer details through authorized workflows.

Restrictions:
- Access only their own company and explicitly authorized placement drives.
- Cannot view unrelated students or companies.
- Cannot change verified academic records or global eligibility policies.
- Cannot approve their own company registration if independent approval is required.
- Cannot directly alter final placement records outside authorized workflows.

### Role 5: Student
Responsibilities:
- Register or sign in securely.
- View and update permitted profile fields.
- Maintain academic information, skills, résumé, and contact details.
- View available placement drives.
- Check eligibility and the reasons for eligibility or ineligibility.
- Apply for eligible placement drives.
- Track application and interview status.
- View offers and final placement outcomes.
- Withdraw an application when permitted by policy.

Restrictions:
- Access only their own profile, applications, résumé, and offers.
- Cannot modify verified academic information or their own placement results.
- Cannot bypass eligibility requirements.
- Cannot submit duplicate applications for the same drive.

## 3. Mandatory Permission Matrix

Implement the following permission rules in the Django backend.

| Feature | Admin | Placement Officer | Coordinator | Recruiter | Student |
|---|---|---|---|---|---|
| Manage users and roles | Full | No | No | No | No |
| Manage global policies | Full | Manage within authorization | View | No | No |
| Manage companies | Full | Manage | View | Own company | No |
| Create placement drives | Full | Yes | No | Submit requests | No |
| Verify student details | Full | Yes | Assigned students | No | Own permitted fields |
| View eligible students | Authorized | Yes | Assigned courses | Authorized applicants | Own eligibility |
| Apply for placements | No | No | No | No | Yes |
| Shortlist candidates | No | Yes | No | Own authorized drives | No |
| Update offers/results | Full | Yes | View | Own authorized drives | View own results |
| View reports | All | Placement reports | Assigned courses | Own drives | Own applications |
| View audit logs | Full | Limited, if authorized | No | No | No |

Apply the principle of least privilege. Every permission must be checked server-side for every relevant request.

## 4. Technology and Architecture

Use a maintainable Django monolithic architecture.

Suggested Django apps:

- `accounts` — authentication, profiles, role assignment.
- `academics` — courses, departments, student academic records.
- `companies` — company profiles and recruiter membership.
- `placements` — placement drives, policies, eligibility evaluation.
- `applications` — applications, shortlisting, interviews, offers.
- `auditlog` — security events and audit records.
- `dashboard` — role-specific dashboards and reports.

Use Django templates with Bootstrap 5 for a responsive interface.

Use Django ORM and MySQL for persistent data storage. Keep database credentials in environment variables loaded from a `.env` file, and provide a `.env.example` containing placeholders only.

## 5. Database Design

Create Django models and migrations for the following entities:

1. User — authentication identity and active status.
2. UserProfile — application role and permitted profile information.
3. Department — academic department.
4. Course — academic programme and assigned coordinator.
5. StudentAcademicRecord — verified CGPA, backlog count, graduation year, and academic status.
6. Company — company details and approval status.
7. RecruiterMembership — association between recruiters and authorized companies.
8. PlacementPolicy — approved eligibility criteria and policy version.
9. PlacementDrive — company, job description, deadlines, job requirements, and status.
10. DriveAuthorization — explicit authorization for company recruiters to manage drives.
11. Application — student, drive, timestamp, and current status.
12. Interview — interview rounds, schedules, and outcomes.
13. Offer — offer details and decision status.
14. AuditLog — actor, action, target, timestamp, outcome, and relevant metadata.

Requirements:
- Define foreign keys, uniqueness constraints, indexes, and appropriate deletion behavior.
- Prevent duplicate applications using a database-level unique constraint on student and drive.
- Use transactions for important multi-step updates.
- Validate academic data and placement deadlines.
- Store uploaded résumés securely and validate file types and sizes.
- Never store plaintext passwords.
- Do not store unnecessary sensitive information in audit logs.

Use Django's built-in user model with a carefully implemented role/profile model, or a custom user model if justified. If using a custom user model, define it before the initial migrations.

## 6. Secure Authentication and RBAC

Implement the following:

- Secure login and logout.
- Password hashing through Django's authentication framework.
- Password validation.
- Session-based authentication.
- CSRF protection on state-changing requests.
- Login throttling or rate limiting.
- Secure session and cookie settings appropriate to the deployment environment.
- Server-side authorization decorators, mixins, permission checks, and queryset filtering.
- Safe handling of unauthorized and forbidden requests.
- Protection against IDOR (Insecure Direct Object Reference).
- Input validation and output escaping.
- ORM-based queries to reduce SQL injection risk.
- Protection against mass assignment and privilege escalation.
- Secure file upload validation.
- Security event logging.

Do not rely on frontend button visibility to enforce authorization.

Examples of required checks:
- A student requesting another student's application must receive a denial.
- A recruiter must not access another company's drives by changing a URL ID.
- A coordinator must not view students from an unassigned course.
- A placement officer must not assign themselves the Admin role.
- An unauthorized user must not access administrative endpoints directly.

Return an appropriate 403 response for forbidden access and 404 where resource concealment is appropriate.

## 7. Policy-Driven Placement Eligibility Engine

Create a centralized eligibility service. Do not duplicate eligibility logic across views or templates.

Support configurable criteria such as:
- Minimum CGPA.
- Maximum active or historical backlogs, as defined by policy.
- Eligible courses and departments.
- Graduation year.
- Required skills.
- Application deadline.
- Student verification status.
- Drive-specific requirements.

The engine must:
1. Load the approved policy and student academic record.
2. Evaluate each applicable criterion.
3. Return an eligibility result and understandable reasons.
4. Re-evaluate eligibility when applying.
5. Validate all criteria on the server, regardless of what the frontend displays.
6. Record the applicable policy version for traceability.
7. Prevent applications after the deadline.
8. Prevent duplicate applications.
9. Avoid exposing private student information to unauthorized recruiters.

Make the rules configurable instead of hardcoding a single CGPA threshold for every company.

Clearly distinguish policy eligibility from recruiter shortlisting and final selection.

### Student workflow

### Recruiter workflow
Login → Manage company profile → Submit drive request → Receive authorization/approval → View eligible applicants → Shortlist → Update recruitment stages → Submit offers/results.

### Placement Officer workflow
Login → Review company → Approve company → Review drive request → Approve and publish drive → Monitor applications → Validate outcomes → Generate reports.

### Course Coordinator workflow
Login → View assigned courses → Review assigned students → Verify academic details → Monitor eligibility and placement progress → Generate course report.

### Admin workflow
Login → Manage accounts and roles → Configure academic structure and policies → Monitor operations → Review audit logs → Generate system reports.

Use explicit status transitions and validate who can perform each transition.

Suggested application statuses:
- Applied
- Under Review
- Shortlisted
- Interview Scheduled
- Selected
- Offered
- Offer Accepted
- Offer Rejected
- Rejected
- Withdrawn

Keep the application's status model consistent across the backend, frontend, reports, and tests.
